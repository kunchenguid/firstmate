# Captain event outbox

This is the maintainer architecture and upgrade contract for Firstmate's optional `fm-captain-event.v1` semantic outbox.
The operator-facing activation and command examples live in [`configuration.md`](configuration.md#semantic-captain-event-outbox-configcaptain-event-outbox).
The exact record, path, validation, and mutation contract lives in the header of [`bin/fm-captain-event.sh`](../bin/fm-captain-event.sh).

## Purpose and boundary

Structured fleet snapshots reconcile current truth, branch outcomes retain Pi supervision activity, and public-followup retains one public commitment's terminal result.
None of those purpose-specific owners is a complete semantic source for visible prose emitted only by a primary or task-worker harness.
The captain-event outbox fills only that gap.
It does not replace or dispatch from those existing stores, and it never interprets terminal presentation, status prose, prompts, or the latest pane.

The P0 producer is Pi-specific while the journal and reader are generic.
The tracked primary extension publishes a primary assistant turn, and the Pi extension generated by `fm-spawn.sh` publishes a task worker's assistant turn.
Both call the same outbox command at Pi's `turn_end` boundary.
That boundary follows `message_end` persistence, so the producer can derive its opaque idempotency key from Pi's stable session-entry identity instead of terminal position, response wording, or a model-supplied identifier.

A Pi assistant response with `stopReason=stop` is explicitly typed as `primary.final` or `worker.final`.
A visible assistant response at another non-error turn boundary is explicitly typed as `primary.message` or `worker.message`.
Provider errors, aborted or deferred responses, and responses with no visible text block publish nothing.
The producer extracts only `type=text` assistant blocks; thinking, tool calls, tool results, diagnostics, provider payloads, user prompts, and terminal bytes have no path into the event builder.

The producer passes trusted source and incarnation identity outside model context.
Primary incarnation is an opaque hash of Pi's session id.
Worker incarnation is the `spawn_gen` already recorded for that exact worker replacement.
The harness event key hashes the Pi session and persisted entry identity.
No custom tool, injected prompt, or model-visible message carries those trusted identifiers.

## Record and ordering

Every canonical journal row has schema `fm-captain-event.v1`, one gap-free home-local `seq`, one derived `event_id`, publication and optional occurrence timestamps, explicit source home and source role, task and incarnation identity, producer and harness-event identity, `audience=captain`, an allowlisted kind, one bounded inert summary, a truncation bit, and an allowlisted reference object.
A source home is `main` or `secondmate:<stable-id>`.
A primary row has no task id; a worker row requires its safe task id.

`event_id` is SHA-256 over the schema, source home, source role, task id, incarnation, producer, and harness event id.
Those fields answer which semantic source event this is; kind, summary, timestamp, and references are the immutable payload attached to it.
A retry with the same identity and payload returns the original sequence without touching journal bytes.
The same identity with a different payload is a conflict and stops publication.

The summary is normalized Unicode, stripped of ANSI and control characters, collapsed to one line, scrubbed for high-confidence credential shapes, and capped at 600 codepoints.
The complete canonical event including its newline is capped at 8 KiB.
Consumers must render `summary` as inert text and make links only from the structured `refs` allowlist.
The current reference keys are `pr_url`, `report_id`, `report_path`, and `branch_outcome_seq`; unknown keys are corruption, not future-looking passthrough data.
The `pr_url` reference accepts only the canonical GitHub pull-request and GitLab merge-request URL forms already owned by [`bin/fm-pr-lib.sh`](../bin/fm-pr-lib.sh); other hosts, userinfo, ports, query strings, fragments, encodings, and extra path segments fail closed.

The P0 spool has a hard 10,000-event ceiling, so its maximum serialized journal is 81,920,000 bytes.
It does not prune or reuse sequence numbers automatically.
Reaching that ceiling stops publication and requires an explicit future retention upgrade or captain-approved intervention rather than silently losing an unacknowledged result.

## Atomic publication and recovery

The outbox lives under mode-`0700` `state/captain-events/` with a mode-`0600` journal, lock, pending records, and consumer acknowledgements.
Every operation validates the complete journal as canonical UTF-8 JSONL with exact keys, matching event hashes, unique identities, gap-free sequence order, hard field bounds, and a terminating newline.
Symlinks, hard-linked files, permissive private paths, malformed pending state, and unknown private entries are refused.

A publisher holds the home-local lock while assigning the next sequence.
It first atomically writes the exact assigned event under `pending/`, then fsyncs and atomically replaces the journal with an old-byte-prefix successor, then removes the pending record durably.
A crash before journal replacement leaves the old journal plus the exact pending event.
A crash after replacement leaves the new journal plus a matching pending event.
`append` and `recover` settle either case idempotently, while `read`, `validate`, and `ack` refuse to cross owed recovery and never salvage a partial tail.
The Pi producer retries a failed emitter process once with the same identity and runs recovery again at session start.

## Consumer protocol

A consumer reads with `read --after <its-cursor>`, optionally paging with `--limit`.
The command validates the complete Firstmate journal and never reads or changes another consumer's position.
The consumer stores its source binding, last sequence, event id, payload hash, and canonical destination row in its own durable transaction.
Same id and same payload is a no-op; same id and different payload stops the source.
A cursor beyond the validated tail, an unexpected truncation, an unknown schema/audience/kind, or any malformed row preserves the consumer's last accepted position and surfaces the source fault.

After that transaction commits, the consumer records ingestion with:

```sh
FM_HOME=/path/to/home bin/fm-captain-event.sh ack \
  --consumer magistrate \
  --through 42 \
  --event-id sha256:<event-id-at-sequence-42>
```

The acknowledgement means the whole range through that exact event and the consumer's own cursor are durably ingested.
It must not be sent after transport receipt, JSON parsing, an attempted database insert, or a transaction that can still roll back.
The private receipt advances monotonically, cannot point beyond or disagree with the journal, and does not delete source bytes or alter any reader's cursor.
This separation keeps independent `after` readers possible while giving a configured soak consumer a durable ingestion receipt.

A first registration must choose bootstrap explicitly.
The usual phone-soak posture is to validate and checkpoint the current tail, acknowledge a nonzero checkpoint only after its source registration is durably committed, then expose new events alongside the current fleet snapshot.
An empty tail requires no acknowledgement.
Historical backfill is a separate bounded operator choice; enabling this outbox must not inject old branch outcomes or old harness transcripts by inference.

## Ownership that remains unchanged

`bin/fm-branch-outcome.sh` remains the sole durable owner of supervision outcomes and their Pi read/processed markers.
The new outbox does not copy its wake field, advance either marker, or make a branch report complete.
A Magistrate adapter may continue to consume branch outcomes as their own source-native stream.

`tasks-axi public-followup` and the `fm-public-followup-*` scripts remain the sole owner of promised public replies and their typed terminal-result transport.
The captain-event journal neither satisfies nor retires a public commitment and never dispatches a second reply.

Herdr remains a runtime and presentation transport.
No Herdr lifecycle, subscription, terminal read, pane revision, or output parser participates in event identity, audience, payload, acknowledgement, or recovery.
Existing task dispatch, status events, completion, PR handling, merge authority, and cleanup behavior are unchanged.

## Upgrade and rollback

The feature is default-off.
An upgraded home without `config/captain-event-outbox` does not run the emitter subprocess and creates no `state/captain-events/` artifact, so existing Firstmate, Pi, other harnesses, and Herdr behavior remain unchanged.

Upgrade in this order:

1. Install a Firstmate release that knows `fm-captain-event.v1`, confirm `bash` and `python3` with the standard POSIX `fcntl` module are available, and leave the flag absent.
2. Run Pi's `/reload` in every already-running primary that will publish and wait for the reload to complete while the flag remains absent; an already-running task worker is not active until the existing worker lifecycle replaces it with an extension generated by this release.
3. Deploy a consumer that strictly validates the schema, keeps its own source cursor and payload hashes, and implements commit-before-ack.
4. Bind the consumer to the intended Firstmate home as a stable source instance.
5. Write exactly `enabled` plus one newline to that home's `config/captain-event-outbox` only after the intended Pi publishers have loaded this release's extensions.
6. Run `validate`, choose and durably record the bootstrap position, then begin `read --after` paging.

Activation is home-local and is not inferred from a Magistrate process, Herdr session, network endpoint, or credential.
A secondmate home is enabled independently so the operator cannot accidentally widen one source binding to every delegated domain.
No network address, authentication token, consumer database id, or callback command belongs in the activation file or an event.

To stop new publication, remove the activation file.
The journal, pending state, and acknowledgements remain private and untouched so re-enabling can resume with the same identities and sequence.
Run `recover` successfully before a planned downgrade if publication recovery is owed.
A consumer may continue to retain its accepted canonical rows, but the disabled Firstmate command intentionally becomes inert rather than offering an undocumented drain path.
Do not truncate, rewrite, renumber, or copy a journal onto another source identity during rollback.

A future schema version must use a new schema name and an explicit consumer negotiation or migration.
Readers reject unknown fields and versions today so an upgrade cannot silently reinterpret identity, audience, private data, or acknowledgement semantics.
