# Accessibility and global audience

Lookup owners:

- [Write accessible documentation](https://developers.google.com/style/accessibility)
- [Write for a global audience](https://developers.google.com/style/translation)
- [Write inclusive documentation](https://developers.google.com/style/inclusive-documentation)

## Global audience

- Prefer simple, consistent vocabulary over idioms and culture-specific references.
- Avoid humor that depends on one locale or moment in pop culture.
- Define acronyms and abbreviations on first use when they may be unfamiliar internationally.
- Avoid seasons; name months or quarters.
- Prefer unambiguous dates; see the main skill's dates section.

## Accessibility checklist

Before treating documentation as done:

- Headings form a logical hierarchy with no skipped levels.
- Link text describes destinations without "click here".
- Lists structure procedures and related options instead of comma-heavy paragraphs.
- Images that convey information have alt text; decorative images use empty alt text.
- No essential content lives only in images, color alone, or iconography without labels.
- Instructions do not rely on direction words such as "above", "below", or "on the right".
- UI controls are named by their visible labels, not by icon shape alone.
- Tables are reserved for true tabular data; introduce each table in the preceding text.

## Inclusive language

Avoid ableist, biased, or demeaning phrasing.
Follow the Google inclusive-documentation guidance for disability, gender, age, and other sensitive topics rather than improvising replacements.
