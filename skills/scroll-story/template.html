Technical walkthrough / durable writes

One request, one durable event.

Follow a new order from the HTTP boundary to the database and out through an event, without losing the side effect if publishing fails.

Create order transaction Scroll to trace

order-service.ts / new transaction boundary

async create(input: CreateOrder) {
  return this.db.transaction(async (tx) => {
    const order = await tx.orders.insert({
      ...input, status: "pending"
    });
    await tx.outbox.insert({
      topic: "orders.created", payload: order
    });
    return order;
  });
}

Both rows commit together; the publisher reads the outbox later.

01 / Entry point

The request enters once.

POST /orders validates the payload and calls OrderService.create. The endpoint does not publish an event itself.

02 / Call flow

Control moves into the service.

The controller delegates one unit of work to OrderService, which owns the transaction and coordinates both repository writes.

03 / New code

The transaction gains an outbox write.

The added lines insert the order and its orders.created payload inside the same database transaction, so neither row can commit alone.

04 / Primary write

The order row lands first.

The service inserts a pending order into orders. This is the business record returned to the caller after the transaction commits.

05 / Durable handoff

The event intent lands beside it.

The service inserts a second row into outbox_events in the same transaction. A later publisher can retry delivery without recreating the order.

06 / Data layer

Three columns carry the change.

orders.status records the initial lifecycle state, while outbox_events.topic and outbox_events.payload describe the message to publish.

07 / Side effect

Publishing is now recoverable.

After commit, an outbox worker publishes orders.created. If the broker is unavailable, the durable outbox row remains available for retry and downstream consumers see no phantom order.

Result

Atomic locally, reliable downstream.

The request now creates its record and its event intent as one commit, separating database consistency from eventual message delivery.
