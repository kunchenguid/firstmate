# Fleet dashboard live core journey

## User outcome

The fleet dashboard shows live fleet state in a real browser at a 390px phone width: each lane with its task title and state on the Board, and the queue and wait reasons on Insights. The one-tap Stuck and Waiting tabs (`#/board?tab=stuck`, `tab=waiting`) hold only those lanes, and a home's count reads against its lane cap (`4 / 3`, amber when over) in the by-home view (`rows=home`), at 390px and 1280px. Tickets (`#/tickets`), in the owner-approved look, splits the backlog into Your asks and System (`kind=system`): a hero counts what is done with one square per ticket, its legend picks the list (Moving, To do, On hold, Done; `show=`), and each row carries its project icon, P0-P3 chip, how far its lane has got and its age, sorted by priority; a Waiting on you tile counts the ask list, which Needs you lists; a computer adds By project beside the list. A card opens its ticket page (`#/tickets?ticket=<home>/<task>`): the description without hold bookkeeping or Main message ids, the captain's words it serves (Your words) with their day, its priority, project and last update as three tiles on a phone, and the thread: on a phone as Activity cards (three, then See all), on a computer as how far its lane has got stage by stage with each stage's time and What happened as a timeline of the latest five, with the fields (priority, project, lead, release, proof, updated) and words beside. Needs you (`#/needs`) leads with a hero of how many questions wait, then one row per question with its type (Yes or no, Pick one, Approval), its age and Open; order and type sit in the filter sheet. A question opens on its own page (`#/needs?ask=<id>`): its type, when it was asked, why it is asked and its answers with the suggested one; prev/next arrows with the position (`2 of 3`) in the header, J/K or the arrow keys on a computer and a swipe on a phone move through the list in its order and type filter, and the ends stop (`ask-{390,1280}.png`, `ask-filter-1280.png`). On touch screens a phone up to 759 px gets the phone design (the dock, no sidebar, 14 px row titles; under 400 px the dock's current view drops its label so the search button keeps its size), a touch tablet at 768 or 1024 px the computer layout with 44 px sidebar rows, and every visible control on Tickets and Needs you takes a 44 px tap; `breakpoints.txt` and `breakpoint-{445,1024}.png` record each width, and the run fails on any other layout or any smaller target. Search (`/` or ⌘K) is a pill over grouped results: Go to, open Tickets by priority, Lanes in flight and Homes, three each until a query; `search-{390,1280}.png` and `.txt` show `layout` finding the ask's ticket and lane. The computer's sidebar foot names the board's reader (`config/owner-name`, else the home's git user.name) and when the board was read, in UTC, red when stale. By release (`#/tickets?by=release`, from the filter sheet with the project and release filters) lays the open items in Next release, After and Later lists: a project's lowest named release (or its items marked next) is Next, a later named release After, no release line Later; the release filter (`release=v0.2.0`) narrows either view. On Metrics, each lifecycle stage opens the Board filtered to that stage (`#/board?stage=ci`, a removable Stage chip) and To land opens it filtered to To merge. A flow reader that fails shows its own error on Insights, not a bare "unavailable". Metrics has a Memory card: free memory against the total, the memory gate's sustained pressure (the lower of the 10 s and 60 s averages, so a 10 s spike does not count) and the watcher's peak over the last hour. Metrics also has Time in stage: every open lane as a dot at its time in its current stage (from the status line that entered it), one row per stage with its median, and the bottleneck named (the stage with the most lane-hours, leaving out lanes on hold); a row opens the Board filtered to that stage. Tickets carry the whole name and description even when `tasks-axi list` cuts them (the build fills them from `show --full`, cached in `state/dashboard/full-text.json`), the Main message that carried the captain's ask, and a Proof row on the ticket page: the lane's completion receipt and the done-done verdict on its merge card. The Metrics Flow card puts GitHub's merges in the fleet's repositories beside the recorded ones: GitHub today, its average before today, how many of GitHub's merges the records hold, and a mark per day on the Landed chart (one read-only `gh pr list` per repository at most every 30 minutes, cached in `state/dashboard/forge.json`; `FM_DASHBOARD_FORGE=off` skips it).

## Drive

Run `done-done run core` from the repo root (it runs `bash fleet-dashboard/run-core-proof.sh` and sets `DONE_DONE_EVIDENCE_ROOT`). The script seeds a throwaway Firstmate home with agent lanes, in-flight, queued and held tasks and one landed task, builds and serves `fleet-dashboard/fm-dashboard.sh` from this checkout against that seed, opens the Board and Insights in headless Chrome with `chrome-devtools-axi`, and fails unless the expected lanes and reasons are on the page. It reads only the seed: stubs replace herdr, quota, device and service probes, and the queue reasons come from this checkout's fleet-flow reader. It needs a Firstmate `bin/` (`FM_BIN`, default `~/firstmate/bin`) for the dashboard's helper scripts.
